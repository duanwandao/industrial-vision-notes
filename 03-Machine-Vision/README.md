# 工业机器视觉上位机学习路线

> 目标岗位：**C# 工业上位机开发工程师（工业机器视觉方向）**。
>
> 学习原则：以能开发、集成、调试一套视觉检测设备为目标。电气和通信知识学到能看懂接口、完成基本配置、定位常见故障和守住安全边界即可；不把电工、PLC 专家、嵌入式硬件工程师和视觉算法研究员四条路线同时作为求职前置条件。

## 求职目标与知识边界（2026-11-08 再次确认）

当前求职目标是 **C# 上位机开发工程师** 和 **工业机器视觉工程师**。核心竞争力是工业软件开发、相机 SDK 集成、图像采集与处理、视觉检测流程和设备软件联调；**不是以 PLC 工程师或电气工程师作为主要求职方向**。

- **主线 P0：** C#/.NET、WinForms/WPF、面向对象与软件架构、异步/多线程、工业相机 SDK、图像采集、成像基础、OpenCV/HALCON、检测算法、日志/异常/部署。
- **系统集成 P0：** PLC 通信、业务握手、请求编号、结果回传、超时、断线恢复。这是上位机与设备协作能力，不意味着要把 PLC 梯形图作为主攻方向。
- **配套 P1：** PLC I/O 与基本流程、步进/伺服状态、编码器反馈、常见电气接口和安全边界；学习目标是看懂设备接口、数据链路和常见故障。
- **暂缓 P2：** 深入电路设计、编码器芯片/光栅结构、PCB、复杂运动控制底层实现，以及与目标岗位无关的 PLC 专家级内容。

学习时以“能否开发、调试和解释一套 C# 视觉检测软件”为判断标准，不以硬件术语数量衡量进度。

## 一、岗位工作模型

典型视觉检测流程：

1. PLC 或设备控制流程发出拍照请求。
2. C# 上位机接收请求，检查相机和流程状态。
3. 相机 SDK 触发采集，返回图像。
4. 上位机将图像交给 OpenCV、HALCON 或项目使用的视觉库处理。
5. 算法输出 OK/NG、位置、尺寸或缺陷信息。
6. 上位机把结果和请求编号写回 PLC。
7. PLC 确认接收结果并控制后续设备动作。
8. 上位机保存图像、检测结果、参数、时间和异常日志。

### P1：现场工作需要的基础

- PLC I/O、24V DC、PNP/NPN、继电器/接触器：能看懂常见触发输入、输出和反馈回路。
- RS-485 与 Modbus RTU：能读设备手册，配置波特率/数据位/校验/停止位/站号，理解寄存器与常见通信错误。
- 步进/伺服：理解使能、运行状态、报警、限位、回零和安全职责；不以独立设计整套运动控制为求职前提。
- 编码器反馈：理解增量式/绝对式、A/B/Z、PPR/倍频、高速计数和位置/速度数据链路；知道它在输送带跟踪、工件定位和线扫相机同步触发中的作用。通常通过 PLC、运动控制器、采集卡或相机 SDK 获取数据，不要求在 Windows 普通程序中直接高速采样 A/B 脉冲。详见[编码器反馈与位置测量](../02-PLC/Encoder-Feedback.md)。
- 以太网诊断：IP、子网、端口、TCP 连接、Ping 的边界和常见断线问题。

### P2：暂缓深入

- UART 过采样、波特率发生器和 MCU 串口寄存器。
- RS-485 收发器芯片内部电路、PCB 布局和高速信号完整性设计。
- PLC CPU 内部实现、复杂电气柜设计和高阶运动控制算法。
- 编码器内部芯片/光学结构设计、PCB 与信号完整性设计，以及 SSI、BiSS-C、EnDat 等复杂协议的底层实现；除非目标岗位或项目明确要求，否则暂缓。

只有当目标岗位明确涉及嵌入式、硬件或底层通信开发时，再提升这些内容的优先级。

## 三、建议学习顺序

1. **C# 上位机工程化**：WinForms 线程模型、异步任务、取消、异常、日志和资源释放。
2. **工业相机 SDK**：以实训设备的真实品牌/型号为准，先跑通枚举、连接、采集、显示、停止和断线恢复。
3. **成像基础**：相机、镜头、光源、视野、工作距离、曝光和增益；先学会获得稳定图像。
4. **视觉算法**：从 OpenCV 或课程指定的 HALCON 开始，完成阈值、轮廓、定位、测量和模板匹配。
5. **PLC 通信与握手**：把相机采集和算法结果接入 PLC 流程，处理请求编号、Ack、Done、超时和重连。
6. **完整项目与部署**：形成可运行的检测软件，补齐参数管理、报警、日志、图像归档和工控机部署。

## 四、建议的第一个综合项目

**C# 工业视觉检测 Demo**

- WinForms 主界面：连接状态、实时图像、检测结果、参数和日志。
- 相机服务：枚举/连接/采集/停止；相机型号未知时先使用 SDK 示例或离线图片模拟。
- 图像处理服务：输入图像，输出结构化结果（OK/NG、测量值、错误码）。
- PLC 通信服务：封装读写、超时和断线处理；先用模拟 PLC 或只读地址验证。
- 流程协调：请求 ID、Busy、Done、ResultAck，防止重复检测和结果错配。
- 结果追溯：保存原图、处理图、结果、参数和时间戳。

## 五、学习边界与待确认信息

- 目前没有足够信息确定实训工业相机的品牌、型号、接口和 SDK 版本；具体 API 不能凭空假设。
- PLC 型号、通信协议、端口和现场地址表需按实际设备资料确认。
- GigE Vision、USB3 Vision 是不同相机接口/标准方向；并非每台相机都同时支持。
- 任何接线、带电测量、设备运动和安全回路操作都应按实训现场规程，由老师/合格人员指导。上位机软件和普通 PLC 逻辑不能替代急停、硬件互锁或安全功能。

**下一步建议：先学习工业相机成像基础（相机、镜头、视野、光源、曝光），然后用实训相机 SDK 跑通“枚举—连接—采集—显示—停止”的最小闭环。**


## PLC 命令与视觉流程的异常恢复

视觉上位机除了完成“请求—采图—检测—结果—确认”，还需要考虑通信中断、上位机重启和 PLC 断电后的事务恢复：

- 使用 RequestId 关联 PLC 请求、图像、检测结果和工件 ID；同一请求重复到达时先查原事务状态，避免重复检测。
- 图像、检测结果和 PLC 消费确认应分别记录持久化状态；不能把内存中的 StepIndex 或单个 Done 位当作完整检查点。
- 断线重连后先重新读取 PLC 当前握手位和 RequestId/ResultId，再决定等待、补交结果或进入人工恢复。
- PLC 本体断电后还要确认工件是否仍在检测工位、运动轴位置是否可信、相机是否完成采集及结果是否保存；回零完成不代表生产流程可以直接从头重放。

详见[PLC 断电恢复与设备状态机](../02-PLC/Power-Loss-Recovery-and-State-Machine.md)和[PLC 命令编号、幂等性与通信恢复](../02-PLC/Communication.md)。本节是系统设计原则，实际恢复策略必须依据设备传感器、持久化能力和现场安全评估制定。
