# 编程中的抽象：从语法、设计模式到软件架构

> 类型：跨语言编程基础 / 编程思维  
> 状态：待学习 / 待验证  
> 适用范围：C#、Java、TypeScript、C++ 等语言；尤其适合结合工业视觉上位机项目理解。

## 1. 核心观点：语法背后通常有一个要解决的问题

学习一门语言时，很容易把知识点看成一串需要记忆的语法：属性、泛型、接口、委托、事件、Lambda、异步、LINQ……

更有效的理解方式是反过来问：

**在这个语法出现之前，程序员反复遇到了什么问题？这个特性把哪种重复结构、复杂机制或约束抽象了出来？**

很多语言特性确实是在把常见的编程思想固化为语言机制，或让某种模式更容易表达。但要避免一个误区：**并不是所有语言特性都是设计模式，也不是所有抽象都只是为了复用代码。**

抽象（Abstraction）可以先理解为：

- 保留当前问题真正关心的特征；
- 隐藏暂时不需要关心的实现细节；
- 明确哪些行为对外可见、哪些细节由内部负责；
- 把稳定的部分与容易变化的部分分开。

抽象的目的不是把代码写得更“高级”，而是降低理解和修改系统时需要同时考虑的细节数量。

## 2. 从重复问题到抽象机制

下面这些 C# 特性，可以从它们解决的问题来理解。

| 特性 / 机制 | 背后的思想 | 主要解决的问题 |
|---|---|---|
| Property（属性） | 封装数据访问 | 用统一的成员访问形式表达读取和修改，同时保留校验、只读等控制能力 |
| Generic（泛型） | 参数化类型与算法 | 让同一套逻辑适用于不同类型，并保留编译期类型检查 |
| Interface（接口） | 契约与依赖抽象 | 调用方依赖能力约定，而不是绑定某个具体实现 |
| Delegate（委托） | 把行为作为数据传递 | 将方法传给其他方法，支持回调和可替换行为 |
| Event（事件） | 发布 / 订阅通知 | 让对象在状态或事情发生时通知订阅者，减少彼此直接依赖 |
| Lambda（Lambda 表达式） | 匿名函数表达 | 就地表达短小行为，减少为一次性操作单独声明方法的负担 |
| async / await | 异步控制流抽象 | 把复杂的异步延续过程写成更接近顺序代码的形式 |
| using | 资源生命周期管理 | 确保实现了 IDisposable 的资源在离开作用域时得到释放 |
| LINQ | 声明式数据查询 | 用统一的查询操作表达筛选、投影、排序和聚合等集合处理 |

这些机制的抽象层次并不完全相同。例如，async/await 是 C# 语言语法和编译器支持；Task 是 .NET 类库中的类型；异步状态机是编译器实现异步控制流时生成的机制。学习时要区分它们。

### 2.1 属性：把数据访问方式统一起来

传统写法可能为字段提供两个方法：

~~~csharp
private string _name;

public string GetName() => _name;

public void SetName(string name)
{
    _name = name;
}
~~~

C# 属性可以表达同样的基本访问意图：

~~~csharp
public string Name { get; set; }
~~~

属性不只是“省略两个方法”的语法糖。它是一种成员访问抽象：调用方使用 camera.Name，类型内部仍然可以控制 getter / setter 的行为，例如校验、只读或限制访问权限。自动属性的后备字段由编译器生成。

### 2.2 泛型：把变化的类型变成参数

如果整数列表、字符串列表、相机对象列表的操作逻辑相同，分别复制三份代码会造成重复。

泛型把“类型”也变成参数：

~~~csharp
public class Box<T>
{
    public T Value { get; set; }
}

var number = new Box<int>();
var cameraName = new Box<string>();
~~~

关键思想是：**把稳定的算法逻辑保留下来，把变化的类型参数化。** 泛型不仅减少重复，还让编译器检查类型是否匹配，避免大量不安全的类型转换。

### 2.3 接口：让调用方依赖能力，而不是具体设备

如果检测服务直接依赖某个厂商的相机类，未来更换相机品牌或使用模拟相机时，业务代码可能需要大量修改。

可以先定义能力契约：

~~~csharp
public interface ICamera
{
    void Open();
    void Close();
    byte[] Capture();
}

public class InspectionService
{
    private readonly ICamera _camera;

    public InspectionService(ICamera camera)
    {
        _camera = camera;
    }
}
~~~

InspectionService 关心的是“能打开、关闭、采集图像的相机”，而不是某个品牌的具体类。

这体现了依赖抽象、降低耦合的思想。接口本身不是某个设计模式；它可以成为策略模式、适配器模式、依赖注入等设计的基础。

### 2.4 委托与事件：把行为传递出去，再通知关注者

委托让方法可以作为参数传递，解决“执行什么行为由调用方决定”的问题。

事件建立在委托机制之上，提供发布 / 订阅的通知形式。它常用于实现观察者模式：

- 发布者负责在某件事发生时发出通知；
- 订阅者通过 += 订阅，通过 -= 取消订阅；
- 发布者不必直接知道所有订阅者的具体类型。

但要注意：**事件本身不会自动切换线程，也不会自动变成异步。** 事件处理程序通常在触发事件的线程上同步执行，除非发布者显式地把工作调度到其他线程或 UI 线程。

### 2.5 async / await：简化异步流程表达

await 让方法可以在等待异步操作完成时暂时让出执行权，并在操作完成后继续执行后续逻辑。编译器会生成状态机来管理暂停和恢复。

它不等于“自动创建一个新线程”。例如，网络 I/O 异步等待通常不需要为等待过程专门占用一个线程；CPU 密集型计算是否放到后台执行，需要另行设计。

### 2.6 using：把释放资源的责任表达清楚

文件、相机连接、图像缓冲区等资源可能需要显式释放。对于实现 IDisposable 的对象，using 语句会在作用域结束时确保调用 Dispose()，其控制流效果可理解为编译器生成了 try/finally。

它不是“让垃圾回收更快”，也不是“所有对象都必须 using”。它解决的是需要确定性释放的资源生命周期问题。

## 3. 不要把语言、类库、框架和设计模式混为一谈

学习 C# 时，很多名词看起来都像“语法”，其实属于不同层次。

| 层次 | 例子 | 它是什么 |
|---|---|---|
| 语言语法 / 类型系统 | class、interface、event、async、泛型 | 语言定义的表达规则与类型能力 |
| 编译器转换 | 自动属性后备字段、async 状态机、迭代器状态机 | 编译器把较高层表达转换为可执行实现的过程 |
| 运行时与基础类库 | CLR、Task、List&lt;T&gt;、IDisposable | .NET 提供的运行环境、类型和通用能力 |
| 框架与 SDK | WinForms、相机厂商 SDK、HSL 通信库 | 面向特定应用场景的组件和 API |
| 设计模式 | 观察者、策略、工厂、适配器 | 对反复出现的软件设计问题的可复用解决思路 |
| 软件架构 | 分层、依赖倒置、模块边界 | 组织较大系统、管理依赖和变化的整体方案 |

例如：

- event 是 C# 语言机制；观察者模式是设计思路。事件可以用来实现观察者模式，但二者不是同一个概念。
- interface 是接口类型机制；策略模式可以使用接口表达可替换策略，但接口本身不等于策略模式。
- Task 是 .NET 类型；async/await 是语言与编译器支持；异步状态机是背后的实现机制。
- 相机 SDK 是厂商提供的 API，不是 C# 语言的一部分。

把这些层次分清，阅读陌生项目或 SDK 文档时就不容易混淆。

## 4. 抽象层次：从硬件到业务系统

一个工业视觉检测系统，可以粗略看成多层能力逐渐叠加：

1. **硬件层**：相机、镜头、光源、PLC、运动机构和工控机。
2. **设备与通信接口层**：相机 SDK、网卡、串口、PLC 通信协议。
3. **语言与运行平台层**：C#、.NET、线程、内存管理、基础类库。
4. **应用框架与组件层**：WinForms、图像处理库、日志库、配置库。
5. **应用架构层**：采集服务、检测服务、设备通信服务、结果存储。
6. **业务层**：产品是否合格、缺陷如何分类、检测结果如何追溯。

高层代码可以调用低层提供的抽象，而不必每次都亲自处理所有硬件细节。但抽象不会让底层复杂性消失：设备断线、SDK 缓冲区生命周期、线程上下文、驱动版本和硬件时序仍然可能影响高层程序。这类现象常被称为“泄漏的抽象”（Leaky Abstraction）。

## 5. 用工业相机采集理解多种抽象如何协作

假设相机 SDK 在采集完成时触发一个回调：

1. **SDK** 负责与相机设备通信，并在采集完成时通知应用。
2. **委托 / 事件** 让应用注册一个处理方法，而不必把业务代码写进 SDK。
3. **回调线程** 决定事件处理程序最初在哪个线程执行；事件不会自动切换到 UI 线程。
4. **缓冲区生命周期** 决定图像数据能否在回调返回后继续使用；如果 SDK 只保证回调期间有效，应用必须按 SDK 文档要求复制或接管数据。
5. **UI 线程调度** 通过 WinForms 的 BeginInvoke 等方式，把控件更新安排到 UI 线程。
6. **检测服务** 接收有效图像数据，执行处理并返回检测结果。

这不是一个语法点，而是语言机制、线程模型、SDK 约定和应用架构共同工作的结果。

示意代码（具体图像类型和复制方式必须按相机 SDK 文档调整）：

~~~csharp
private void Camera_ImageCaptured(
    object? sender,
    ImageCapturedEventArgs e)
{
    // 假设这里已经按 SDK 约定取得了可安全持有的图像副本。
    var imageCopy = CopyImageAccordingToSdkRules(e);

    if (InvokeRequired)
    {
        BeginInvoke(new Action(() =>
        {
            pictureBox.Image = imageCopy;
        }));
        return;
    }

    pictureBox.Image = imageCopy;
}
~~~

这段代码也说明了一个重要原则：**抽象帮助我们分工，但不会替我们自动解决线程安全、资源所有权和设备安全问题。**

## 6. 抽象的收益与代价

抽象并不是越多越好。

| 收益 | 可能的代价 |
|---|---|
| 降低重复代码 | 过度抽象会增加间接层 |
| 隔离实现变化 | 抽象边界设计错误时，修改反而更困难 |
| 方便替换实现和测试 | 调试时需要跨越更多接口和调用层 |
| 统一团队协作约定 | 过多通用化会让简单问题变复杂 |
| 隐藏不必要的细节 | 底层行为仍可能通过性能、线程和生命周期暴露出来 |

实用判断：

- 如果有多个实现、变化频繁或需要模拟测试，接口和抽象可能有价值。
- 如果同一逻辑重复出现，泛型、方法或公共组件可能有价值。
- 如果只是一次性、非常简单的逻辑，不必为了“设计模式”强行增加类和接口。
- 先理解真实问题，再决定是否抽象；不要先设计一套庞大框架，再寻找使用场景。

## 7. 以后学习任何语言特性，都问这五个问题

1. **原始问题是什么？** 没有这个特性时，程序员通常怎样实现？
2. **抽象了什么？** 哪些细节被隐藏，哪些能力被暴露？
3. **稳定与变化分别是什么？** 哪些代码可以复用，哪些部分应该由调用方提供？
4. **背后谁在工作？** 是编译器、运行时、基础类库、框架，还是 SDK？
5. **代价是什么？** 是否增加间接层、隐藏线程行为、引入生命周期或性能问题？

用这五个问题学习，语法就不再是一张需要死记硬背的清单，而会成为一组有来由、有边界、有适用场景的工具。

## 8. 自测与实践

### 自测问题

1. 为什么说泛型不只是为了少写几份代码？
2. interface 是不是一种设计模式？它和策略模式有什么关系？
3. event 与观察者模式有什么关系？事件触发时是否一定切换线程？
4. async/await 是否意味着自动创建后台线程？
5. Task、async 和异步状态机分别属于什么层次？
6. 为什么相机 SDK 的图像回调不能随意把缓冲区引用保存到 UI 线程使用？
7. 抽象为什么可能“泄漏”？工业设备断线和图像缓冲区生命周期能说明什么？
8. 什么情况下不应该为了复用而引入接口或设计模式？

### 小实践：让检测服务不依赖具体相机

1. 先写一个具体的 MockCamera 类，提供打开、关闭和采集图像的模拟方法。
2. 提取 ICamera 接口，让检测服务只依赖 ICamera。
3. 再写一个不同实现（例如 RecordedImageCamera，从本地图片模拟采集），不修改检测服务。
4. 观察：哪些代码保持不变？哪些代码因设备实现不同而变化？
5. 如果增加“采集完成通知”，再使用委托 / 事件，并验证事件处理程序运行在哪个线程。

**完成标准：** 能用自己的话解释每个抽象隔离了什么变化、调用方仍然必须知道什么，以及它带来了什么代价。

## 9. 关注点分离（SoC）与“课题分离”不是同一个概念

两者都能让人联想到“边界”，但来源和解决的问题不同：

| 概念 | 所属领域 | 核心问题 |
|---|---|---|
| 关注点分离（Separation of Concerns, SoC） | 软件工程 | 如何把不同职责拆开，降低模块耦合 |
| 课题分离（常见于阿德勒心理学通俗讨论） | 心理学/人际关系 | 如何判断某项选择、行动和结果主要由谁承担 |

在设备上位机中，SoC 的例子是把 UI 展示、业务流程、设备协议和串口 I/O 分开；课题分离不能直接作为软件架构术语。两者最多类比为“明确边界”，不可当成同一理论。

## 10. 驱动、SDK、接口与协议的层次

“驱动”在不同语境中含义不同，沟通时要说明层次：

1. **操作系统设备驱动**：操作系统用来识别、管理和访问硬件的驱动程序，例如 USB 转串口芯片对应的 Windows 驱动。
2. **厂商 SDK**：厂商提供的 API、库、头文件/程序集、示例和文档；它可能调用底层驱动，也可能封装网络或串口通信。
3. **应用层设备适配器/通信封装**：项目自己写的类，例如 `JialiLedController`，把 `SetBrightness(channel, value)` 转成厂商协议命令，并解析响应。团队口语里可能称它为“设备驱动”，但它不是 Windows 内核驱动。
4. **物理接口**：UART TTL、RS-232、RS-485、USB、Ethernet 等，规定电气/传输层面的连接方式。
5. **通信协议**：定义命令格式、帧边界、校验、应答与错误处理，例如厂商自定义 ASCII 协议或 Modbus RTU。

示意调用链：

~~~text
WinForms UI
    ↓
业务服务 / 检测流程
    ↓
应用层设备适配器（例如 JialiLedController）
    ↓
SerialPort API / 厂商 SDK
    ↓
Windows 串口驱动 / USB 转串口芯片
    ↓
物理接口与设备
~~~

SerialPort 负责 COM 端口字节收发，不等于 RS-232/RS-485 电气接口，也不等于 Modbus RTU 协议。应用层设备适配器的价值是隐藏命令编码、校验和解析细节，但不应掩盖超时、断线、线程上下文和资源生命周期。

## 11. 自测

1. SoC 为什么能降低 UI 与设备协议的耦合？如果更换光源品牌，哪些层应该变化？
2. `JialiLedController` 为什么更准确地说是应用层设备适配器，而不是 Windows 内核驱动？
3. SerialPort、RS-485 和 Modbus RTU 分别属于哪一层？
4. SDK 与驱动有什么关系？SDK 是否一定包含操作系统驱动？

## 12. 本专题结论

> 学习编程，不是单纯积累语法，而是理解抽象。语法是表达抽象的工具；设计模式是组织对象协作的经验；框架和 SDK 则把更大范围的能力封装起来。

真正的进步，是看到陌生代码时能够判断：它在解决什么问题、为什么这样分层、哪些细节被隐藏、哪些责任仍然需要自己承担。
