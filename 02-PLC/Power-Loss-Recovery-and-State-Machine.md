# PLC 断电恢复、命令状态与设备状态机

> P1｜待学习 / 待验证｜2026-11-08  
> 面向 C# 上位机开发与工业机器视觉岗位。PLC、运动控制和电气知识用于设备集成、通信与异常诊断，不作为当前求职主线。本文是通用设计学习，不是某一台设备的可直接执行程序。

## 一、先区分三种故障场景

| 场景 | 仍可能工作的部分 | 主要不确定性 |
|---|---|---|
| 仅上位机与 PLC 网络断开 | PLC、驱动器和机构可能继续运行 | 上位机暂时失去观察和下发命令的能力 |
| PLC 本体断电再上电 | 机械机构可能惯性停止、被制动或受外力移动 | 非保持变量、脉冲计数、命令记录和坐标有效性可能丢失 |
| C# 上位机进程重启 | PLC 可能一直运行 | 上位机内存中的任务、缓存状态和未持久化结果丢失 |

不能把“通信恢复”“PLC 重新上电”和“上位机程序重启”当成同一种恢复事件。恢复策略要先识别故障类型，再读取双方状态。

## 二、三种状态维度必须分开

不要用一个 IsRunning 或 IsConnected 代表整台设备。建议至少分开管理：

| 维度 | 示例状态 | 含义 |
|---|---|---|
| 连接状态 ConnectionState | Online / Offline / Reconnecting | 上位机能否与 PLC 正常通信 |
| 设备状态 MachineState | Initializing / Checking / HomingRequired / Homing / RecoveryRequired / Ready / Running / Fault | 设备整体当前处于什么运行阶段 |
| 命令状态 CommandState | Idle / Sending / Accepted / Running / Completed / Rejected / Failed / Interrupted / Unknown | 某一条具体命令的生命周期 |

三个维度可以同时处于不同状态。例如网络断开时，PLC 控制的轴可能仍在 Running；上位机连接状态是 Offline；上位机无法确定当前命令结果，因此 CommandState 对上位机可能是 Unknown。

### Interrupted、Unknown、Failed 的区别

- **Interrupted：** 有证据确认命令执行过程中被断电、急停或其他中断打断；它不是“正常完成”。
- **Unknown：** 证据不足，无法判断命令是否被 PLC 接收、是否执行或是否完成。例如 Ack 返回途中断网。
- **Failed：** 已明确知道命令被拒绝或执行失败，例如 PLC 明确返回拒绝原因或驱动器故障。
- **Completed：** 有对应命令编号的完成反馈，且结果数据有效。

不能因为没有收到 Done 就直接认定 Failed；也不能把 Unknown 擅自改成 Interrupted 或 Completed。

## 三、命令握手：Ack 不等于 Done

一条典型命令可包含：

| 字段 | 方向 | 作用 |
|---|---|---|
| CommandId | C# → PLC | 识别本次命令 |
| CommandType / Parameters | C# → PLC | 命令类型与参数 |
| Req | C# → PLC | 请求执行 |
| AcceptedCommandId | PLC → C# | PLC 已接受的命令编号 |
| Ack | PLC → C# | PLC 已接受/登记请求 |
| Busy | PLC → C# | PLC 正在执行 |
| Done | PLC → C# | 本次命令完成 |
| CompletedCommandId | PLC → C# | 已完成命令的编号 |
| ErrorCode | PLC → C# | 拒绝或执行异常原因 |

以上是协议字段示例，不是 S7-200 SMART 固定地址。正式项目要由 PLC 与上位机共同定义地址、类型、单位、读写方、超时、复位顺序和编号规则。

### 为什么 Done 必须与 CommandId 匹配？

假设第一次命令 1001 已完成，但 Done 仍保持为 1。第二次命令 1002 刚发出时，如果上位机只读取 Done=1，就可能把上一次的完成信号误认为本次完成。

判断当前命令完成，至少要满足：

- Done 表示有效完成；
- CompletedCommandId 与当前 CommandId 一致；
- 对应结果数据已有效写入；
- 没有同一命令的错误/拒绝状态。

因此，孤立的 Done 布尔位不足以代表某条命令完成。

## 四、CommandId 与幂等性

**幂等性（Idempotency）**是协议对同一逻辑请求重复提交时的去重约定，不是简单地“多发几次”。

建议 PLC 对已接收命令维护去重记录：

1. 相同 CommandId + 相同参数，且仍在执行：返回该命令当前状态，不重新启动。
2. 相同 CommandId + 相同参数，且已经完成：返回原完成状态和结果，不重复执行。
3. 相同 CommandId + 不同参数：拒绝并报告协议错误。
4. 真正的新操作：分配新的 CommandId。
5. 同一逻辑命令因通信超时需要重试时，不能随意生成新 ID；是否允许用原 ID 重试，取决于 PLC 是否可靠保存去重记录及双方协议约定。

**关键限制：** 如果 PLC 断电后命令去重记录丢失，就不能保证重试仍然幂等。需要有经过验证的保持/持久化机制，或在重启后先进入状态核对与恢复流程。CommandId 能识别命令，不会自动保存机械位置，也不会自动防止所有重复动作。

编号还需约定唯一性范围、计数器回绕、PLC/PC 重启后的编号恢复，以及同一编号在不同设备/生产批次中的隔离方式。

## 五、断电后为什么不能相信开环步进轴的保存位置？

开环步进控制中，PLC 可能根据输出脉冲数量计算理论位置。例如上次记录 640 mm、目标 1000 mm。这个 640 mm 可能只是“按已发出的脉冲推算出的指令位置”，不是编码器反馈的机械实际位置。

断电前后可能发生：

- 步进电机负载过大或加减速不合适，已经丢步；
- 电机失去保持力矩后，机构被外力移动；
- 联轴器、皮带或传动机构发生打滑；
- 机械惯性、制动器或负载状态导致最终位置不同于软件记录。

因此，在题设“没有编码器且断电后位置无法由其他可靠方式确认”的情况下，不能直接从记录的 640 mm 继续运动到 1000 mm。

### 不同反馈方案的恢复边界

| 方案 | 断电后位置可信度 | 恢复注意事项 |
|---|---|---|
| 开环步进、无编码器 | 通常无法确认真实机械位置 | 在安全条件满足后，按设备流程重新回零 |
| 增量式编码器 | 取决于计数器/驱动器是否保持计数；普通计数可能丢失 | 核对计数保持、驱动器状态和参考点，必要时重新回零 |
| 绝对值编码器 | 可能保留单圈或多圈绝对位置 | 仍需核对圈数/电池、机械联接、坐标偏置、驱动器与标定状态 |

编码器提供位置反馈，不等于机械坐标必然正确；反馈链路、联轴器、丝杆、原点偏置和机械标定仍会影响结果。

### 原点信号为 0 能说明什么？

原点传感器当前为 0，只能按已确认的接线和逻辑映射解释当前输入状态。它不能单独证明轴在哪里，也不能证明回零路径安全。限位均未触发同样不能证明机构位置已知或运动路径没有障碍。

## 六、回零不是上电后的无条件第一动作

回零本身会让机构运动。必须先确认设备允许执行回零。典型检查项包括：

1. 按设备风险评估确认急停、安全门和安全回路状态；软件状态不能替代硬件安全功能。
2. 确认驱动器 Ready、无有效报警，驱动使能与制动器状态符合设备要求。
3. 检查正负限位和原点输入是否合理，确认输入极性/常开常闭逻辑与现场接线一致。
4. 确认机械运动路径、回零方向、速度、搜索距离和可能的干涉风险。
5. 按具体设备的回零流程执行搜索、脱离、低速再接近、偏移等步骤（实际步骤依 PLC/运动控制器和机构设计）。
6. 检查回零完成反馈、坐标有效标志和必要的轴状态，再进入后续恢复判断。

不能仅因为原点输入为 0 就高速回零；不能直接把当前位置变量写成 0 来伪造回零完成。普通限位、软件互锁和 C# 按钮禁用也不能替代适当的硬件安全设计。

## 七、推荐的上电恢复流程

~~~text
PowerOn
  -> Initializing
  -> Connecting
  -> ReadSnapshot
  -> Checking
       -> Fault（存在驱动/安全故障）
       -> HomingRequired（轴位置无效）
       -> RecoveryRequired（存在中断任务）
       -> Ready（无待处理任务且条件满足）
  HomingRequired
  -> 安全检查后受控回零
  -> RecoveryRequired
  -> 核对命令、工件、流程检查点
       -> 创建新的恢复命令（关联原 CommandId）
       -> 或 ManualRecovery（等待人工判断）
  -> Ready
~~~

流程说明：

- 上电后先初始化和建立通信，不自动恢复 Running。
- 读取 PLC 保持数据、当前握手位、驱动器反馈、限位/原点状态及上位机持久化记录。
- 对位置无效的轴，先进入 HomingRequired；回零前完成安全与机械条件检查。
- 对原命令状态为 Running 且断电中断的任务，标记 Interrupted；证据不足则标记 Unknown。
- 回零完成不代表生产任务可以直接重放，还要核对工件是否仍在原位、上一步是否已经产生不可逆副作用。
- 如果允许恢复，创建新的恢复命令 ID，并记录它与原命令 ID 的关联；不要把新执行伪装成原命令从未中断。
- 无法确认产品、机械或流程状态时，停留在 RecoveryRequired / ManualRecovery，等待人工确认。

## 八、Checkpoint：机器视觉流程如何恢复？

Checkpoint（检查点）是经过确认、已持久化的流程进度，不只是内存中的 StepIndex。

例如视觉检测设备：

| 步骤 | 完成条件/持久化证据 |
|---|---|
| 产品到达工位 | 产品 ID 与工位/传感器状态关联 |
| 相机拍照 | 采集成功，图像缓冲区有效 |
| 图像保存 | 图像文件/对象已持久化，并记录路径或标识 |
| 算法检测 | 检测任务完成，记录算法版本与结果 |
| 结果保存 | 结果与产品 ID、图像 ID、Command/Request ID 关联并持久化 |
| PLC 消费结果 | PLC 已确认读取对应结果 |
| 产品下料 | 下料动作完成且有对应反馈 |

检查点应在该步骤的实际副作用和必要数据已经确认后再更新。比如“拍照成功”不等于“图像已经保存”；“算法返回 OK”不等于“结果已写入 PLC 并被 PLC 消费”。

断电恢复时：
- 如果图像已持久化但结果未完成，可以评估对原图重新运行算法，避免重复拍照。
- 如果图像未保存，只有确认工件仍在正确工位且可以安全重新触发时，才考虑重新采集。
- 如果结果已保存但 PLC 是否消费未知，先按 RequestId/ResultId 握手核对，避免重复下料或把旧结果分配给新工件。

## 九、C# 上位机的建模方式

不要把连接、设备和命令状态塞进一个 enum，也不要让 UI 按钮直接随意改状态。可以分别定义：

~~~csharp
public enum ConnectionState
{
    Online,
    Offline,
    Reconnecting
}

public enum MachineState
{
    Initializing,
    Checking,
    HomingRequired,
    Homing,
    RecoveryRequired,
    Ready,
    Running,
    Fault
}

public enum CommandState
{
    Idle,
    Sending,
    Accepted,
    Running,
    Completed,
    Rejected,
    Failed,
    Interrupted,
    Unknown
}
~~~

建议由 MachineController/CommandManager 统一执行状态转换校验，再通过 event 通知 WinForms UI。UI 负责展示状态和发起用户意图，不直接把 PLC 反馈改写成任意状态。

CancellationToken 只能请求 C# 等待/后台任务协作取消，不等于 PLC 运动停止。取消上位机任务后仍需通过可靠的设备控制与反馈流程确认轴状态；安全停止由相应硬件/安全控制功能承担。

## 十、常见误区与正确判断

| 误区 | 正确判断 |
|---|---|
| TCP 重连成功 = 设备恢复 | 只说明通信重新可用，必须重新读取设备与命令状态 |
| 写入命令成功 = 电机已启动 | 写入成功、PLC 接受、设备执行、动作完成是不同层次 |
| Done=1 = 当前命令完成 | 必须核对 CompletedCommandId 与当前 CommandId |
| 超时 = PLC 没收到 | 可能是请求已执行但响应丢失 |
| 重试就换新 CommandId | 同一逻辑命令的重试应沿用原 ID，但前提是去重协议有效 |
| PLC 保存了 640 mm = 机械就在 640 mm | 可能只是指令位置，不是实际反馈 |
| 原点输入为 0 = 可以直接高速回零 | 需确认信号逻辑、机械路径、速度和安全条件 |
| 回零完成 = 原任务可直接重跑 | 还需核对工件、流程检查点和重复副作用 |
| C# 取消等待 = 设备停止 | 必须由设备控制逻辑与反馈确认，安全功能不能依赖普通软件取消 |

## 十一、面试回答模板

**问：PLC 运行中突然断电，重新上电后如何恢复？**

可以回答：

“我不会直接重发上一次的运动命令。首先区分是上位机断网还是 PLC 本体断电；重新连接后读取 PLC 的保持数据、当前命令编号、驱动器报警、限位、原点和轴反馈。对于没有编码器的开环步进轴，PLC 保存的位置可能只是按脉冲计算的指令位置，不能代表机械实际位置，因此要在确认安全和机械路径后按设备流程重新回零。原命令根据证据标记为 Interrupted 或 Unknown，再结合产品 ID 和流程 Checkpoint 判断能否恢复。如果允许恢复，就创建新的恢复命令并关联原命令；不能确认时转人工处理，不自动重放。”
