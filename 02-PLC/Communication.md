# PLC 通信、类型与结果处理

> P0｜待学习｜2026-10-31｜Q010–012、Q034–036（项目所需部分）、Q043–047、Q049、Q053。

一句话：通信把双方约定的数据编码到协议中；网络连通、读写成功和设备动作成功是三层不同证据。

IP 定位网络接口，掩码帮助判断是否本地直达，MAC 用于链路转发，TCP 提供有序字节流，端口标识服务。同网段还可能因 VLAN、防火墙、冲突或服务未启用而不通；ping 仅验证相应 ICMP 可达，不证明 S7 服务和地址可访问。

VS 是开发工具，WinForms 是界面框架，S7netplus/HslCommunication 是协议库。不能因为都是西门子就推断所有 CPU 与库组合兼容；S7netplus 对 SMART 的具体支持须查版本，原项目实际用了 HslCommunication。以项目配置确认 API，不照搬最新文档。

## 数据协议与离线测试（Q012）

先约定 VW200 的类型、范围、读写权限和单位。2002 可用 16 位有符号数表达，但不能用 WriteFloat 写入同一 2 字节目标。用内存字节数组模拟 PLC 区域：写入两个字节后按同一字节序读回 2002，并测试越界、超时和写入失败；该模拟不证明真实协议握手兼容。实际 PLC 需审批后的测试环境和地址表，本次不连接。

`WriteFloat(address, 20)` 在只有 float 形参时发生 int→float 隐式转换；`20f` 明确 float，`(short)20` 明确 short。`short x = 20` 是范围内常量赋值；不存在通用 short 字面量后缀。若有 int/short/float 重载，重载决议取决于参数静态类型，不能靠运行时值猜测。TS 的 number 习惯不能直接套到 C# 和 PLC 二进制布局。

## 结果、异常与并发

原项目 ReadBool/ReadFloat 返回 OperateResult<T>，成功后才读 Content；WriteBool/WriteFloat 返回非泛型 OperateResult。失败结果与抛异常都要处理，不能仅 catch 而忽略 IsSuccess。

lock(sync) 串行化同一实例使用同一锁的路径，不是跨进程锁，也不保证未用锁的连接/断开安全。Monitor 同线程可重入，因此原项目 ReadPosition 中嵌套 ReadFloat 的同锁不是必然死锁；Home 持锁 Sleep 则会延迟其他请求。不要在 lock 中 await。

连接检查可提取“检查+加锁+调用”的 Execute<T>，写操作可能需非泛型重载；这是重构建议，未改项目或验证 API。连接状态、超时、断开必须纳入共同策略。`isConnect` 是历史布尔状态，不能代替实时读写结果。

工业用途：周期读取位置，失败时保留错误和时间戳；写命令后读取 PLC 应答/设备反馈。Q053 缺原测试工具上下文，数字 1 无法确定代表长度、站号还是值，维持待核实。

自测：区分“连接失败”“地址错误”“结果成功但轴没动”，每类列一条下一步证据。源码依据及配置见[项目笔记](../04-Industrial-Projects/Dual-Axis-Jog.md)。

## 双网卡配置：电脑同时连接互联网与 PLC

### 场景与本次配置

一台 Windows 笔记本可以通过两张独立网卡同时连接两个网络。本次实践中，USB 转网口用于互联网，电脑自带的 Realtek 网口连接 PLC。两张网卡分别配置，不需要把 PLC 网线接入互联网路由器。

| 设备/网卡 | 本次观察到的 IPv4 | 子网掩码 | 默认网关 | 作用 |
|---|---|---|---|---|
| PLC | 192.168.0.2 | 待从 PLC 配置确认 | 待确认 | 工业设备 |
| Realtek PCIe GbE Family Controller（电脑自带网口） | 192.168.0.6 | 255.255.255.0 | 未设置 | PLC 专用网卡 |
| ASIX AX88179 USB 3.0 to Gigabit Ethernet Adapter（USB 转网口） | 192.168.65.79 | 255.255.255.0 | 192.168.65.1 | 互联网网卡 |

以上 IP 来自本次 `ipconfig /all` 截图。USB 网卡通过 DHCP 自动获取地址；Realtek 网卡使用手动配置的静态地址。截图还显示 USB 网卡 DNS 为 114.114.114.114 和 8.8.8.8。未记录 MAC 地址，避免把与学习无关的硬件标识写入笔记。

**当前判断：** 电脑两张网卡使用不同网段，Realtek 网卡没有默认网关，USB 网卡具有默认网关。这是“PLC 直连网卡 + 互联网网卡”常见且合理的配置方式。需要注意：尚未从 PLC 本体或工程中确认 PLC 的子网掩码，因此“电脑与 PLC 同网段”的结论以 PLC 掩码也是 255.255.255.0 为前提；还要确认 192.168.0.6 没有与其他设备冲突。

### 为什么两张网卡可以同时工作

网卡是电脑连接以太网或无线网络的接口。每张网卡可以有自己的 IP 配置。Windows 根据路由表决定目标 IP 应从哪个接口发送：

- 访问 192.168.0.2 时，如果 PLC 的掩码确实是 255.255.255.0，目标属于 192.168.0.0/24，Windows 会通过 Realtek 网卡直接访问 PLC。
- 访问互联网地址时，目标不属于上述本地网段，Windows 通常使用 USB 网卡上的默认路由（下一跳为 192.168.65.1）。
- 如果两张网卡配置了重叠网段，或者出现多个不合理的默认网关，可能导致路由选择不符合预期。

路由选择不是简单地“永远走某张网卡”：Windows 优先考虑匹配目标的最长前缀路由；同等前缀的路由还会受路由度量值等因素影响。可用 `route print -4` 检查实际 IPv4 路由表。

### IP、子网掩码、网关和 DNS

- **IP 地址：** 标识网络中的接口。例如电脑 Realtek 网卡为 192.168.0.6，PLC 为 192.168.0.2。
- **子网掩码：** 决定哪些地址属于本地子网。若双方均为 255.255.255.0，则网络前缀为 192.168.0，地址 192.168.0.2 与 192.168.0.6 属于同一 /24 网段。
- **默认网关：** 访问本地子网之外目标时使用的下一跳。PLC 直连网卡只负责访问同一 PLC 网段时，通常可以留空；互联网网卡则需要路由器作为默认网关。
- **DNS：** 将域名解析为 IP。PLC 通信若直接填写 IP 地址，PLC 专用网卡通常不需要 DNS；互联网网卡需要可用 DNS 完成域名解析。
- **MAC 地址与 ARP：** 在以太网本地链路上，电脑需要把同网段目标 IP 解析为目标 MAC 地址，再把以太网帧发出去。ARP 负责 IPv4 地址到链路层地址的解析。跨网段通信时，电脑通常解析的是下一跳网关的 MAC，而不是远端服务器的 MAC。

### 配置原则与注意事项

1. PLC 网卡的静态 IP 必须与 PLC 的实际地址规划匹配，不能只凭习惯猜测 PLC 的子网掩码。
2. 静态 IP 必须未被其他设备占用；还要确认 PLC 和电脑接在正确的物理网口或交换机上。
3. 在这种独立双网段场景中，PLC 网卡通常不设置默认网关和 DNS；互联网网卡保持 DHCP 自动获取，前提是网络确实由 DHCP 提供地址。
4. 两张网卡最好使用不同网段。本次电脑侧分别是 192.168.0.0/24 和 192.168.65.0/24，没有重叠。
5. 如果 PLC 网络需要访问其他网段、经过路由器或由现场网络统一管理，应遵循现场网络管理员给出的地址、网关和安全策略，不要机械套用“网关留空”。
6. 不要为了让 Ping 成功而随意关闭防火墙或更改 PLC 程序。先确认网络规划、网线和设备通信服务。

### Windows 网络诊断命令

在 PowerShell 中执行：

```powershell
# 查看网卡、IP、掩码、网关和 DNS 等详细配置
ipconfig /all

# 查看网卡名称、状态、物理接口描述和链路速度
Get-NetAdapter | Format-Table Name, InterfaceDescription, Status, LinkSpeed

# 查看 IPv4 路由表，检查默认路由和 PLC 网段路由
route print -4

# 测试 PLC 的 ICMP 可达性（本次 PLC 地址）
ping 192.168.0.2

# 查看本机 ARP 缓存；先尝试与 PLC 通信后再观察
arp -a
```

解释结果时要分层：

- `ipconfig /all` 检查本机配置，不证明链路或 PLC 服务可用。
- `ping` 测试 ICMP。Ping 成功说明相应 ICMP 报文可达；Ping 失败也可能是设备禁用了 ICMP，不能单凭它断定 PLC 通信失败。
- `arp -a` 可帮助检查本地 IPv4 地址是否解析出 MAC，但缓存可能过期或尚未生成。
- TCP 端口测试只有在端口和协议已确认时才有意义。不同 PLC 型号、协议和服务使用的端口可能不同；S7、Modbus TCP 和厂商专用协议不能混为一谈。
- 即使 TCP 端口可连接，也不代表 PLC 地址读写、数据类型和设备动作都正确。最终仍需用匹配型号与协议的通信库进行受控读写验证。

## PLC 与 C# 上位机的应用层握手（2026-11-03）

> 场景：PLC 到位后请求工业相机拍照；C# 上位机采图并运行视觉检测；PLC 读取 OK/NG 结果。以下地址和协议是教学示例，需由项目双方共同约定，不是 S7-200 SMART 固定协议。

### 为什么不建议只发一个短暂置位

例如 C# 执行：

~~~csharp
plc.Write("M0.0", true);
await Task.Delay(20);
plc.Write("M0.0", false);
~~~

这只是把 PLC 的 M 位短暂置为 1，再恢复为 0。可能出现两种漏接：

1. C# 写入 M 位后，PLC 程序在该位为 1 的时间段内没有执行到读取它，等程序再次读取时位已经回到 0。
2. PLC 把请求位短暂置 1 又清零，而 C# 每 100 ms 才轮询一次，读取时可能前后都是 0。

第一种是 PLC 程序扫描与 M 位状态保持之间的时序问题；第二种是 PLC 状态变化与上位机轮询之间的时序问题。**M 位不是输入映像区**，不要把“C# 写 M 位”和“物理输入 I 点采样”混为一谈。

对物理数字输入的短脉冲，普通输入映像也可能漏采；应按 CPU/输入点规格评估输入滤波、脉冲捕捉、高速计数器或中断。对 PLC 与 PC 之间的业务命令，通常优先设计保持请求直到对方确认的握手。

### 握手不等于 TCP 三次握手

TCP 三次握手用于建立 TCP 连接；这里讨论的是 PLC 与 C# 应用程序之间的**业务层握手**。TCP 连接成功、HslCommunication 写操作返回成功，都不能单独证明 PLC 程序已经接受命令或相机已经完成检测。

### 示例地址表

| 地址 | 变量 | 写入方 | 含义 |
|---|---|---|---|
| M0.0 | Trigger | PLC | 请求执行一次视觉检测，收到确认前保持为 1 |
| M0.1 | TriggerAck | C# | 上位机已接受本次请求 |
| M0.2 | Busy | C# | 正在采图/检测/等待结果确认 |
| M0.3 | Done | C# | 结果数据已写好且有效 |
| M0.4 | ResultAck | PLC | PLC 已读取并消费本次结果 |
| M0.5 | Ready | C# | 上位机空闲且允许接受新请求 |
| VW200 | RequestId | PLC | 本次请求编号 |
| VW202 | ResultId | C# | 本次结果对应的请求编号 |
| VW204 | ResultCode | C# | 示例：0=NG，1=OK，2=检测错误 |

这些地址仅供说明。正式项目应统一地址表、数据类型、读写权限、默认值、超时、复位条件和任务编号回绕规则，不能直接覆盖现有工程地址。

### 一次完整的握手时序

1. **空闲**：C# 设置 Ready=1，Busy=0，Done=0；所有上一笔握手位已复位。
2. **PLC 发请求**：PLC 先写入新的 RequestId，再设置 Trigger=1，并保持 Trigger 和 RequestId 不变，直到收到 TriggerAck。
3. **C# 接受请求**：上位机轮询到 Trigger=1，确认 Ready=1 且没有正在处理的任务，读取 RequestId，设置 Ready=0、Busy=1、TriggerAck=1。TriggerAck 表示“已接受”，不是“检测已完成”。
4. **PLC 清请求**：PLC 看到 TriggerAck=1 后清除 Trigger。
5. **C# 结束请求交接**：C# 观察到 Trigger=0 后清除 TriggerAck=0；Busy 继续保持 1，视觉任务仍可在后台运行。
6. **C# 发布结果**：采图和算法完成后，先写 ResultId、ResultCode（以及需要的测量值/错误码），确认每次写操作成功后，最后才设置 Done=1。Done 和结果数据保持稳定。
7. **PLC 确认结果**：PLC 看到 Done=1，核对 ResultId 与 RequestId 一致，读取并保存结果，然后设置 ResultAck=1。
8. **C# 撤销 Done**：上位机看到 ResultAck=1 后清除 Done=0。
9. **PLC 清除结果确认**：PLC 看到 Done=0 后清除 ResultAck=0。
10. **回到空闲**：C# 看到 ResultAck=0，确认事务结束后设置 Busy=0、Ready=1。PLC 必须等 Ready=1 且上一笔握手位清零后才能发下一笔请求。

~~~mermaid
sequenceDiagram
    participant PLC
    participant PC as C# 上位机
    participant CAM as 工业相机
    participant HAL as HALCON
    PLC->>PLC: 写 RequestId=n
    PLC->>PC: Trigger=1（保持）
    PC->>PC: 检查 Ready/Busy/RequestId
    PC->>PLC: TriggerAck=1, Busy=1, Ready=0
    PLC->>PLC: 看到 TriggerAck，清 Trigger
    PC->>PLC: 看到 Trigger=0，清 TriggerAck
    PC->>CAM: 采集图像
    CAM-->>PC: 返回图像
    PC->>HAL: 执行定位/测量/缺陷检测
    HAL-->>PC: 返回结果
    PC->>PLC: 写 ResultId/ResultCode，最后 Done=1
    PLC->>PLC: 核对 ID，读取并保存结果
    PLC->>PC: ResultAck=1
    PC->>PLC: 清 Done=0
    PLC->>PLC: 看到 Done=0，清 ResultAck=0
    PC->>PLC: 看到 ResultAck=0，Busy=0, Ready=1
~~~

### C# + HslCommunication 实现要点

- 在后台任务/工作线程中轮询 PLC，避免同步通信阻塞 WinForms UI 线程；UI 状态更新再通过 WinForms UI 线程切回。
- 每次读取/写入都检查 HslCommunication 的 OperateResult.IsSuccess，失败时记录地址、操作、时间和错误信息；不要只 catch 后忽略结果。
- TriggerAck 只在上位机已接受请求、已记录 RequestId 后置位；同一个 RequestId 不得因多次轮询而重复启动检测。
- 结果发布顺序是先写结果数据与 ResultId，最后写 Done。任一步失败，不得提前宣布 Done。
- 不能把 plc.Write(...) 成功等同于业务完成；它只说明通信库报告本次写操作成功，PLC 程序仍需通过状态握手确认消费。
- 若底层是同步 HslCommunication API，可将通信调用放入受控后台任务；同一个 PLC 客户端的并发访问应遵守项目中的锁/串行化策略。不要在 UI Timer 回调中执行可能长时间阻塞的同步通信。
- 超时应分开设计：请求接收超时、视觉检测超时、结果确认超时、通信断线超时。超时后进入明确故障状态，不要无条件重发并造成重复拍照。
- 断线重连后先读取 Trigger/Busy/Done/Ack/RequestId/ResultId，再决定恢复、等待或人工复位；不要直接把所有握手位清零。
- RequestId 用于识别一笔事务和去重；还要约定计数器回绕、PLC/PC 重启、旧结果残留和重复请求的处理。

### 最小状态约束

- Trigger=1：请求尚未被上位机接受，PLC 不得提前清除。
- TriggerAck=1：上位机已接受请求；PLC 可撤销 Trigger。
- Busy=1：本次检测事务尚未完全结束。
- Done=1：ResultId/ResultCode 等结果字段有效且保持稳定。
- ResultAck=1：PLC 已消费结果；上位机可以撤销 Done。
- Ready=1：上位机空闲、通信健康、无未完成事务，允许下一次请求。

握手能提高命令交接可靠性，但不是安全回路。急停、限位、驱动安全功能和设备危险能量隔离不能由 C# 握手或普通 M 位替代。

## 串口通信、以太网与 RS485（2026-11-04）

> 学习状态：待学习 / 待验证。岗位定位：C# 工业上位机开发（工业机器视觉方向）。本节目标是能选对通信方式、看懂设备手册、完成基本配置和故障分层排查；不要求深入 UART 芯片或电路设计。

### 先把几个容易混淆的概念分开

| 名称 | 主要解决的问题 | 典型例子 |
|---|---|---|
| 串行通信（Serial） | 数据位按顺序逐个传输，是一种数据传输方式 | UART 串口、RS-232、RS-485 场景 |
| UART | 常见异步串行收发机制，规定字符帧的起始位、数据位、校验位和停止位 | 9600、8、N、1 |
| RS-232 / RS-485 | 电气接口标准，规定信号电气特性和驱动/接收要求 | 仪表、变频器、控制器的串口端口 |
| Ethernet（以太网） | 局域网链路技术，涉及物理层与数据链路层 | RJ45 网口、交换机、工业相机 |
| IP / TCP / UDP | 网络层寻址、传输层通信机制 | IP 地址、TCP 端口、UDP 数据报 |
| Modbus RTU / Modbus TCP | 应用层设备数据读写协议 | 读取变频器频率、写入控制字 |

关键结论：

- “串口”不等于 RS-485；串口通信是一类传输方式，RS-232/RS-485 是不同的电气接口标准。
- UART 不等于 RS-485。UART 负责常见异步串口数据帧的组织；RS-485 收发器把逻辑侧信号转换为差分电信号。
- RS-485 不等于 Modbus RTU。RS-485 可以承载 Modbus RTU，也可以承载其他协议；Modbus RTU 也可以运行在 RS-232 等串行接口上。
- 以太网不等于 TCP/IP，TCP/IP 也不等于 Modbus TCP。它们位于不同层次，必须组合后才能完成具体设备通信。

### 串口通信与 UART：理解配置即可

串行通信把数据按时间顺序逐位发送。常见 UART 异步字符帧包含起始位、数据位、可选校验位和停止位。

例如设备手册中的 `9600, 8, N, 1`：

| 配置 | 含义 |
|---|---|
| 9600 | 波特率，表示每秒 9600 个符号；常见二进制 UART 中通常对应 9600 bit/s |
| 8 | 8 个数据位 |
| N | No parity，无校验位 |
| 1 | 1 个停止位 |

双方的波特率、数据位、校验位、停止位必须匹配。若配置不一致，可能出现无响应、乱码、校验错误或间歇性通信失败。

当前岗位所需：能读懂并配置这些参数，知道起始位/数据位/停止位的用途即可。暂不需要研究 UART 采样电路、过采样、波特率发生器或 MCU 外设寄存器。

### RS-485：掌握现场使用原理

RS-485 是平衡差分电气接口标准。接收端主要判断两根信号线之间的差分电压，而不是只看某一根线相对地的电压。

- 两根线受到相近的共模干扰时，差分电压可能基本保持不变，因此有较好的抗共模干扰能力。
- 抗干扰不是绝对的：共模电压仍须处于收发器允许范围内，布线、接地/参考、屏蔽和终端匹配仍然重要。
- A/B、D+/D- 等标记在不同厂商资料中可能存在命名或极性差异。不能只凭字母猜极性，必须按两端设备手册确认。
- 常见两线制使用同一对线收发，属于半双工：同一时刻通常只能有一方驱动总线。常见四线制使用独立发送/接收线对，可实现全双工。
- 多设备通常采用总线型（主干串接、支线尽量短）拓扑。不要随意做长支线或星形接线。
- 终端电阻通常放在总线物理两端，并按电缆特性阻抗选择；常见约 120Ω 只是典型值，不是每台设备都并一个电阻。偏置/空闲态电阻是否需要，取决于收发器和设备设计。
- 信号参考地、屏蔽层和 PE 的连接必须依据设备手册与现场接地规范；不要把 A/B、0V、N、PE 当成可互换端子。

现场排查顺序可先从低风险项目开始：

1. 确认两端确实使用 RS-485，且两线/四线模式一致。
2. 对照手册核对 A/B（或 D+/D-）定义、接线和总线拓扑。
3. 核对波特率、数据位、校验位、停止位、从站地址和协议。
4. 确认主站轮询、从站响应及驱动使能没有发生总线冲突。
5. 再检查终端/偏置、线缆、屏蔽与参考地，以及设备错误码。

### 以太网通信：与你的 C# 上位机更直接相关

常见分层关系：

| 层次/要素 | 作用 | 例子 |
|---|---|---|
| Ethernet | 本地链路与物理传输 | 网线、交换机、MAC 帧 |
| IP | 跨网络寻址与路由 | 192.168.1.20 |
| TCP / UDP | 传输层机制 | TCP 连接与有序字节流、UDP 数据报 |
| 端口 | 标识目标设备上的服务 | Modbus TCP 常用默认端口 502 |
| 应用协议 | 定义请求、响应和数据含义 | Modbus TCP、S7 通信、GigE Vision |

C# 连接 PLC 时，不能只知道 IP 就认为通信一定可用。还要确认 PLC 型号、启用的服务、协议库兼容性、端口/连接方式、数据地址与类型、超时和返回结果。

Ping 成功只说明相应 ICMP 测试可达，不证明 PLC 的应用服务、寄存器读写或设备动作成功。TCP 端口连接成功也不等于应用协议和数据地址正确。

工业相机若采用 GigE Vision，虽然也使用以太网，但它是面向机器视觉相机的通信标准，不是 Modbus TCP。相机 SDK、采集流、触发和图像缓冲区需要按相机厂商与接口标准学习。USB3 Vision 则用于符合该标准的 USB 3.0 工业相机。

### Modbus RTU 与 Modbus TCP

| 对比 | Modbus RTU | Modbus TCP |
|---|---|---|
| 常见承载方式 | 串口，常见 RS-485 | Ethernet + TCP/IP |
| 帧特点 | 从站地址、功能码、数据、CRC；帧间有规定的静默间隔 | 使用 MBAP 报文头，通过 TCP 传输；不使用 RTU 帧尾 CRC |
| 常见用途 | PLC 与变频器、仪表通信 | PLC、工控机与支持 Modbus TCP 的设备通信 |

Modbus TCP 的默认端口通常为 TCP 502，但实际项目仍以设备手册和网络配置为准。寄存器的含义、缩放比例、数据类型和地址偏移通常由设备厂商定义，不能只凭“40001”之类的显示编号推断实际报文地址。

在 S7-200 SMART 学习语境中，`MBUS_CTRL` / `MBUS_MSG` 是 Modbus 主站串行通信相关指令；它们不是 RS-485 接口本身，也不是以太网 TCP 通信指令。具体 CPU、端口、指令参数和地址规则应以对应版本系统手册为准。

### 对 C# 工业机器视觉上位机岗位，学到什么程度？

| 内容 | 优先级 | 达标标准 |
|---|---|---|
| C# 通过 Ethernet 与 PLC 通信 | P0 | 会配置连接、读写已确认地址、处理超时/断线/返回结果 |

## 命令编号、幂等性与通信恢复（2026-11-08）

> 学习状态：待学习 / 待验证。面向 C# 工业上位机与工业机器视觉岗位；PLC 命令恢复属于设备集成能力，不等同于 PLC 编程岗位主线。

### 先区分三种不同的“成功”

| 层次 | 证据 | 不能据此推出什么 |
|---|---|---|
| 网络/连接成功 | TCP 连接或通信会话可用 | PLC 业务逻辑已接受命令 |
| 通信写入成功 | 通信库返回写操作成功 | 设备已经启动或动作完成 |
| 命令被接受 | PLC 返回 Ack，并记录对应命令编号 | 动作已经完成 |
| 命令执行完成 | Done 与完成命令编号匹配，且无对应错误 | 生产流程后续步骤已经全部完成 |

Ack 表示“已接受/已登记”，Done 表示“本命令已完成”。二者不能互换。

### CommandId：把反馈和具体命令关联起来

对上位机下发给 PLC 的命令，可约定以下字段（仅为协议示例，不是 S7-200 SMART 固定地址）：

| 字段 | 方向 | 含义 |
|---|---|---|
| CommandId | C# → PLC | 本次命令的唯一编号 |
| CommandType | C# → PLC | 命令类型 |
| CommandParameters | C# → PLC | 目标位置、速度等参数 |
| Req | C# → PLC | 请求位，按协议保持到 PLC 确认 |
| AcceptedCommandId | PLC → C# | PLC 已接受的命令编号 |
| CompletedCommandId | PLC → C# | PLC 已完成的命令编号 |
| Ack / Busy / Done | PLC → C# | 接受、执行中、完成状态 |
| ErrorCode | PLC → C# | 拒绝或执行异常的原因代码 |

只有在 Done 有效、CompletedCommandId 与当前 CommandId 相同，并且结果状态符合协议时，C# 才能把当前命令标记为 Completed。

例如，旧命令 1001 的 Done 仍为 1，而当前命令是 1002。此时 Done=1 只是旧状态，不能认定 1002 已完成。单独检查一个布尔位不足以关联事务。

### 幂等性与重复请求

幂等性不是“多发几次都没关系”，而是协议对同一逻辑请求的重复提交有明确去重语义。

1. 同一逻辑命令重试时，沿用原 CommandId，不要因为超时就立即生成新编号。
2. PLC 已收到相同 CommandId、相同参数且仍在执行时，返回原命令当前状态，不再次启动动作。
3. PLC 已完成相同 CommandId 时，返回原完成状态和结果，不重复执行。
4. 相同 CommandId 却携带不同参数时，应拒绝并报告协议错误，不能把它当成新命令。
5. 真正的新操作才分配新 CommandId；编号的持久化、回绕和重启后的命名空间必须由协议约定。

**重要边界：** 去重能力依赖 PLC 保存的命令记录。如果 PLC 断电后去重记录也丢失，就不能假设幂等性仍然成立。此时必须先做恢复状态核对，不能盲目重发。CommandId 能关联事务，但不能证明机械位置或工件状态正确。

### 超时、断线与重连

- 发送超时不等于 PLC 没收到命令；可能是 PLC 已接受，但 Ack 返回途中丢失。
- 同一命令的通信重试不应随意换成新 ID；只有在 PLC 具备可靠去重记录且协议明确允许时，才可按原 ID 重试。
- 重连后先读取 Req、Ack、Busy、Done、AcceptedCommandId、CompletedCommandId、ErrorCode 及必要的设备反馈，再判断命令处于何种状态。
- 不要因为重新连接成功就清零所有握手位，也不要把上位机缓存状态直接当成 PLC 当前状态。
- 网络断开但 PLC 仍运行，与 PLC 本体断电是不同故障：前者可能只是上位机失去观察能力；后者还可能使非保持变量、反馈计数或设备坐标失效。

### 三个状态维度不要混成一个 bool

| 维度 | 示例 | 回答的问题 |
|---|---|---|
| ConnectionState | Online / Offline / Reconnecting | 上位机能否与 PLC 通信？ |
| MachineState | Checking / Homing / Ready / Running / Fault | 设备当前处于什么运行状态？ |
| CommandState | Sending / Accepted / Running / Completed / Interrupted / Unknown | 某条具体命令执行到哪一步？ |

例如网络断开时，PLC 控制的轴可能仍是 Running；上位机连接状态是 Offline；当前命令结果对上位机可能是 Unknown。三者并不矛盾。

详细的状态定义、断电恢复、回零前检查和视觉流程检查点见[PLC 断电恢复与设备状态机](Power-Loss-Recovery-and-State-Machine.md)。

### 与视觉检测流程的联系

如果 PLC 请求 C# 拍照检测，RequestId 用于把 PLC 请求与图像/检测结果关联；如果 C# 向 PLC 下发运动命令，CommandId 用于把运动命令与 PLC 反馈关联。两者都是事务关联编号，但方向和业务含义不同，不要混用。

检测结果发布应先写结果数据及 ResultId，最后置 Done；PLC 核对编号并消费结果后再按握手协议确认。断线恢复时，还要核对产品 ID、图像是否持久化、检测结果是否保存，避免把旧结果误配给新工件。

**安全边界：** 握手、CommandId、看门狗和 C# 状态机都不是安全回路。急停、危险运动防护、限位及驱动安全功能必须由符合风险评估要求的硬件/安全控制方案承担。
